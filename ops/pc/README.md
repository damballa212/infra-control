# PC personal Windows / CachyOS

El broker del VPS autentica la PC por SSH a través del túnel privado FiberHome, con una llave Ed25519 dedicada. Las claves privadas solo viven en `/etc/infra-control-wol`, nunca en Docker ni en el navegador. `pc_known_hosts` fija una identidad para cada SO; el status autenticado verifica MAC y devuelve SO/bootId.

Linux: instalar `cachyos-control.sh` root-owned en `/usr/local/sbin/infra-control-pc` y el wrapper en `/usr/local/bin/infra-control-pc-command`. La línea dedicada authorized_keys usa `restrict,command="/usr/local/bin/infra-control-pc-command"`. El wrapper pasa SSH_ORIGINAL_COMMAND como un argumento literal; el helper admite solo status/off/windows/cachyos/default-windows/default-cachyos. BootNext para cambios temporales se conserva como antes. El cambio persistente valida Boot0000 como Windows Boot Manager y Boot0004 como GRUB CachyOS por sus rutas EFI, confirma `GRUB_DEFAULT=0` y la primera entrada CachyOS, guarda BootOrder/BootNext en `/var/lib/infra-control/boot-default.previous`, cambia solo BootOrder y verifica su lectura posterior; no toca BootNext ni reinicia. Si cambia la tabla o GRUB deja de coincidir, el helper falla cerrado. Este equipo ya tenía sudo NOPASSWD para el usuario; no se amplió sudo.

Windows: `windows-control.ps1` se instala como `C:\ProgramData\InfraControl\command.ps1`, `windows-power.ps1` como `power.ps1` y `windows-boot-default.ps1` como `boot-default.ps1`. Directorio con permisos solo SYSTEM/Administrators. `boot.json` protegido contiene los identificadores de las entradas UEFI instaladas, comprobados con `bcdedit /enum firmware`; el helper valida la ruta de `bootmgfw.efi` y que CachyOS apunte a `grubx64.efi`, nunca a “CachyOS Installer”. El cambio persistente respalda BCD y orden firmware, reordena `{fwbootmgr}`, verifica el readback y conserva la secuencia temporal. No cambia el timeout ni el default interno de Windows Boot Manager. La clave en administrators_authorized_keys conserva las demás claves y fuerza command.ps1, sin forwarding/PTY. El comando valida su allowlist; las escrituras registran una tarea SYSTEM que ejecuta power.ps1 cinco segundos después para poder devolver ACK. BCD bootsequence se cambia una sola vez al solicitar un SO solo para el siguiente arranque. Apagado/reinicio no usa /f.

Estado de producción verificado el2026-10-21: el broker del VPS informa la PC `online:true`, `controlled:true`, SO Windows y `bootId` presente, pero sin `defaultSystem`; el helper UEFI nuevo no está instalado. El panel rechaza la selección persistente con HTTP503 antes de crear intención o enviar comandos. La clave SSH del broker solo permite operaciones allowlisted y no da shell ni copia de archivos; el Mac no tiene un alias SSH Windows y su alias CachyOS no respondió en la última prueba directa. Esto no significa que la PC esté apagada: el túnel del VPS sí la alcanza. Instalar el helper Windows, el reporter CachyOS y verificar firmware requiere un canal autorizado de aprovisionamiento. No cambiar el arranque ni reiniciar para validarlo durante una sesión de trabajo.

`GET /status` no escribe. `POST /power/off`, `/power/windows`, `/power/cachyos` autentica primero el sistema actual y solo envía un comando fijo; el destino puede ser el propio sistema activo (reiniciar en el mismo sistema), que se confirma con un bootId nuevo. No acepta shell, destinos ni payloads arbitrarios. Enfriamiento30s, una mutación por intención, sin reenvíos automáticos. La API comprueba SO objetivo y bootId nuevo; para apagado exige ACK y dos ausencias SSH con el túnel sano, sin afirmar medición eléctrica.

El usuario autorizó explícitamente las pruebas de reinicio/apagado/WOL. No confundir dicha autorización de instalación con permiso permanente para reiniciar durante consultas futuras: cada acción de energía de UI solicita confirmación y advierte sobre las sesiones abiertas.

## Avisos salientes (configuración de producción)

El panel usa `desktop.reportTokenHashes` con SHA-256 independientes para Windows y CachyOS. Cada host conoce únicamente su token y endpoint HTTPS `/api/desktop/events`. No reutilizar el bearer de Hermes.

Linux: `reporters/linux-reporter.py` en `/usr/local/lib/infra-control/reporter.py`, configuración root600 `/etc/infra-control-reporter.json` con endpoint/token, unidad `reporters/infra-control-reporter.service`, estado privado `/var/lib/infra-control-report`. Instalar además `cachyos-power.sh` como `/usr/local/sbin/infra-control-pc-power`.

Windows: `reporters/windows-reporter.ps1` en `C:\ProgramData\InfraControl\reporter.ps1`, configuración `reporter.json` con endpoint/token en el mismo directorio protegido. Tarea `InfraControlReporter`: SYSTEM, AtStartup sin demora, ejecución ilimitada, IgnoreNew, permite batería y reintentos del daemon. Arrancarla también tras instalar.

Aviso online inmediato, heartbeat10s, TLS verificado sin redirects. Secuencia por bootId persistida mediante reemplazo atómico y backup. El panel retira arranques antiguos. Tras45s sin señal se muestra unreachable, nunca apagado confirmado. Los helpers anuncian intención y programan recuperación40s si la transición no ocurre. El estado push y las comprobaciones de resultado leen solo SQLite; SSH queda limitado a preflight y órdenes explícitas.

Pruebas offline reporter: `python3 -m unittest discover -s ops/pc/reporters -p 'test_*.py'`. Nunca incluir configuraciones reales en el repo.

## Instalar los helpers de Windows (sistema por defecto)

El broker no puede copiar archivos, así que la instalación es un paso local con permisos de administrador. Junto a `install-windows-helpers.ps1` deben estar `windows-control.ps1` y `windows-boot-default.ps1` (se pueden enviar por Taildrop al equipo Windows). En PowerShell como Administrador: `powershell -ExecutionPolicy Bypass -File .\install-windows-helpers.ps1` (con `-CheckOnly` solo comprueba). El instalador confirma administrador y MAC, exige que `C:\ProgramData\InfraControl` no sea escribible por usuarios normales, respalda `command.ps1` y `boot-default.ps1` como `*.bak-<fecha>`, instala ambos con BOM UTF-8 (necesario para los acentos en Windows PowerShell 5.1) y ejecuta solo lecturas: `boot-default.ps1 -Status` y `command.ps1 status`. No modifica `boot.json`, BCD, orden de arranque, tareas ni `authorized_keys`, y no reinicia. Si `defaultSystem` sale `unknown`, el panel seguirá rechazando el cambio hasta que `boot.json` coincida con las entradas UEFI reales. Probado con PowerShell 7.6 en macOS (sintaxis y lectura del orden con salidas simuladas de `bcdedit` en inglés y español, incluida la entrada «installer» rechazada); no ejecutado en Windows.

## Canal directo de órdenes (agente de la PC)

Es un acelerador del camino SSH: cada SO de la PC corre un agente que mantiene una conexión HTTPS saliente en espera (`GET /api/desktop/commands`, long-poll de 25 s) y ejecuta órdenes de una lista cerrada (`off`, `windows`, `cachyos`; `ping` para medir latencia). Usa el mismo token por SO de los avisos. No abre puertos, no acepta shell ni argumentos libres y no concede lectura. El panel solo lo usa si el agente declaró la capacidad `power`; si no está conectado o no confirma en 3 s, la orden va por SSH como siempre. Una orden ya entregada nunca se reenvía por SSH (una sola ejecución); el agente confirma antes de ejecutar y rechaza si el `bootId` no es el de su arranque.

- **Windows:** `reporters/windows-commander.ps1` + `reporters/install-windows-commander.ps1` (Administrador; `-CheckOnly`, `-Caps ping,power`, `-Remove`). Instala `C:\ProgramData\InfraControl\commander.ps1` y la tarea `InfraControlCommander` (SYSTEM, al arrancar, como el reporter). Las capacidades están en `commander.json`; por defecto solo `ping`.
- **CachyOS:** `reporters/linux-commander.py`, `reporters/infra-control-commander.service` y `reporters/install-linux-commander.sh` (root; `--check`, `--caps ping,power`, `--remove`). Capacidades en `/etc/infra-control-commander.json`; por defecto solo `ping`. Llama al mismo helper `/usr/local/sbin/infra-control-pc`.
- **Activación por fases:** instalar con `ping`; comprobar `desktopChannel` en `GET /api/system/health` (o la fila `desktop-channel` de `settings`); solo entonces, con una persona presente, cambiar a `power` y probar una orden real. Para volver a SSH basta quitar `power` de las capacidades o retirar el agente.
- **Medido el 2026-10-21 (Windows, `ping`):** ida y vuelta de 407–419 ms (3 muestras) frente a ~4 s por SSH autenticado. El ping se envía solo cuando el agente se conecta tras más de 40 s sin sondear.
- Pruebas: `python3 -m unittest discover -s ops/pc/reporters -p 'test_*.py'` y `npm test` (`desktop-commands`, `desktop-channel-api`).
